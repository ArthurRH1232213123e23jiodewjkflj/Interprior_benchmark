# LIBERO envs — one directory per env

`tasks/libero/envs/<env_id>/` — **22 directories**, 21 distinct geometries.
Generated by `build_env_dirs.py`; regenerate, do not hand-edit.

```
envs/<env_id>/
├── mesh.npz         HOPE scan (verts/faces/uv), verts already in METRES
├── points_obj.npy   the 16 canonical surface points, float32 [16,3]
├── env.yaml         extent, bbox, sha256, which LIBERO uids/scenes map here
├── <env_id>.obj     spawnable mesh      (written by build_object_urdf.py)
└── <env_id>.urdf    spawnable asset     (references <env_id>.obj by name)

All 22 carry these five. One exception: alphabet_soup/ also holds 7 leftovers from
the 0813 single-object worked example (.usd, config.yaml, textured.obj/.mtl,
texture_map.png, textures/, usd_src/). Residue, not a second contract -- and no
script here regenerates them, so `rm -rf envs` loses them.
env_registry.json    all 22 records + geometry aliases
cases.json           95 runnable trajectories (env_id + goal_npz)
reachability_report.json   why the other 35 are out
```

## Why 22 and not 130

130 is the **trajectory** count, not the env count. What a sim needs to spawn an
env is the object asset — and that is 22 things. Measured, not assumed:

**Support height is already normalised away.** The pointflow pipeline rebases
each task's support surface into `goal_traj`:

| support | n | world z0 (mean) | base-frame z0 (mean) |
|---|---|---|---|
| floor | 10 | 0.0476 | 0.0464 |
| low_table | 32 | 0.4712 | 0.0247 |
| table | 88 | 0.9133 | 0.0053 |

0.87 m apart in world frame, all within 0.005–0.046 m of the table in base frame.
`world_z - base_z` ranges −0.005 → 1.126 (std 0.29), so this is **not** one
constant robot_base being subtracted — the per-task surface height really is
absorbed. So one table height serves all 130; support and z0 are not env axes.

**Assets are one-per-name.** 22 mesh basenames, each with exactly **one** sha256
across all 130 tasks (0 basenames with multiple hashes). `points_obj` is
bit-identical across every task sharing an env — 43 for the bowl. Surface points
depend on the asset, not the trajectory.

**Suffixed uids are scene instances, not objects.** 26 uids collapse to 22 assets:
`akita_black_bowl_{1,2,3}`, `butter_{1,2}`, `yellow_book_{1,2}` each share one mesh.
And `new_salad_dressing` / `salad_dressing` are **byte-identical** — 21 real geometries.

Rejected alternatives: 130 dirs (79 would be one env with a different path, and
`pointflow/`'s existing 130-way mesh duplication already costs 106 MB of the
116 MB there); 51 `(object,support,z0)` combos (two of three axes are fake per
the table above); 23 bddl scenes (cuts across assets — one scene holds several).

## What is in cases.json and what is not

95 of 130. Excluded: **12 no_motion** (`ENV_LIST.csv` marks them; the target
never moves, so there is nothing to follow) and **23 xy out of envelope**.

The envelope is the cube donor's measured reach (`tasks/build_task`):
xy ≤ 0.687 m, z ≤ 0.653 m, 3D ≤ 0.907 m. LIBERO fits z and 3D **130/130 and
130/130**, but only **107/130** on xy — LIBERO reaches further sideways than
the xArm7 does. Same shape as the authored cube trajectories (4/7 usable): a
trajectory outside the envelope is a task out of distribution, not a policy failure.
Per-env exclusions are in `reachability_report.json`; the bowl loses 14 of 43.

## Still not runnable

`driver.py` has **zero** handling for `goal_source: authored_npz` — the field has
been declared in `suites/suite.py` since the cube work but nothing reads it in
this package. And LIBERO ships **no robot joint data at all** (it is Franka +
gripper, ours is xArm7 + Wuji), so a teacher replay here is structurally
impossible — `envs/episode.py` requires `robot_joint_pos`/`_target`.

The path in is `bench_cube_val/envs/authored_episode.py`: it synthesises a full
DerivedEpisode from a donor shard plus an authored `[K,7]`, which is exactly the
shape of this data. That donor's canonical cloud is a 0.06 m cube, though, and
these objects are 0.077–0.354 m — the substitution that was exact for authored
cube paths is **not** exact here. Resolving that is the next real decision.

## Metrics change meaning

`guide_tracking_*` and `demo_success` compare against a **teacher recording**.
There is no teacher rollout behind a LIBERO trajectory, so the same formulas
measure agreement with a target path: "did it follow", not "did it reproduce".
These numbers must never be averaged in with held-out shard results.
