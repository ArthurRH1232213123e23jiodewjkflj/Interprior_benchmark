## 4. exp04 跑出 0/200，和 zjw 79/200 的四个原因

我们（200 条，647 帧）：`demo_success 0/200`、`ever_lifted 5/200`、guide 64.0mm。
zjw（同 ckpt、同 200 条、同 647 帧）：**`demo_success 79/200`、`ever_lifted 149/200`、
guide 中位数 18.2mm**。

逐 case 对比 case000（同一 `episode_uid`）：他 guide 19.4mm、方块举到 1.059m；
我们 guide 158.5mm、`rise_max_m` **5.8 微米**（纹丝未动）。

四个缺陷，按发现顺序 —— **每一个都掩盖着下一个**。

### A. 一个 runner 被 N 个并行 env 共用（**未修**）

`bench_replay.py:401` `if policy_mode and index > 0: continue` —— 一个 shard 里 N 个 case
被当成 N 个并行 env，共用**一个 runner、只装 case 0 的 plan**。200 条那次每个 worker
50 个 case，其中 49 个在追 case 0 的目标。

- **诊断**：server 日志只有一次 `plan received`，而 `ticks = frames × n`
- **实测**：case 0 单 env 跑，guide **158.5mm → 20.8mm**，几乎追平 zjw 的 19.4mm；
  within3cm 4.8% → 81.9%

README 自己写着「每个 env 一个模型实例，共用会互相污染」。
`_upstream/servers_ref/policy_server_actor.py:104` 有正确模式（`store[env_id]` + `reset_flag`）。

**难点**：exp04 每个 env 需要完整 runner（含各自的 plan 和 chunk 状态），
而现在协议的 PLAN 帧**不带 `env_id`**。要么扩协议，要么让 driver 一 case 一进程。

### B. plan 从错误的源帧切（已修）

zjw 切 `policy_plan[121:768]`；我们切 `[0:647]`。**同样 647 帧但内容错位 121 帧**。
物体在帧 463 才动，所以我们的 plan 让策略先等，然后越追越错。

**最锐利的诊断 —— 手对、臂错**：前 300 帧 action MAE
手部 **0.001 rad**（zjw 0.0096，几乎完美，且手会正常闭合 0.588 vs teacher 0.604 rad），
手臂 **0.384 rad**（zjw 0.057，差 6.7 倍）。
手是 absolute 不受 plan 时序影响；手臂要追 plan，所以错位全落手臂。

逐帧 arm j7：

| 帧 | 0 | 50 | 100 | 200 |
|---|---|---|---|---|
| teacher | 0.0000 | 0.0000 | 0.0000 | 0.5942 |
| 我们 | 0.0119 | 0.5977 | **1.2500** | 2.1888 |

第一帧几乎完美 → **不是起点错，是 plan 内容错**。

**`start_frame` 和 plan 切片是两个独立偏移。** `suite.start_frame` 只决定仿真从哪帧起，
plan 仍从 `[:horizon]` 切。所以我先前单独试 `start_frame=121` **无效**（20.8mm 逐位相同）。
已给 Suite 加 `plan_source_start` 字段。

**注意**：`plan_source_start=121` 要配 `--frames 0`（保留完整 episode），
否则 `--frames 647` 把 episode 裁短，`[121:768]` 只剩 526 帧，会触发新加的守卫报错。

### C. chunk 缓存每 tick 被丢弃（已修）

三处叠加：

1. `SubprocessAdapter.commit_action()` 是**继承基类的空方法**，IPC 上什么都没过线
2. `chunk_invalidation_tolerance_rad=0.0` —— `changed = max|action - _last_action| > tolerance`，
   而 `_last_action` 是**上一帧动作**，机器人在动必然不同 → chunk 每 tick 作废
3. commit 在 clamp **之前**（`:467` vs `:479`），提交的是未裁剪值，PhysX 执行的是裁剪后的

**诊断量**：

```
inference_calls / frames  =  647/647 = 1.00   ← 坏，每 tick 重规划
                             ~22/647 = 0.034  ← 好，chunk 生效
```

修后实测 `calls_per_tick` 1.00 → **0.034**（22 次推理 vs 647）。

### D. 录制的初始关节位没过线（已修）

`SubprocessAdapter.reset()` 收下 `robot_joint_pos` 却**从不发送**，server 只能用
第一个 tick 的仿真实测值（settle 之后的读回值）。zjw 用录制值
`episode.arrays["robot_joint_pos"][start]`。exp04 是 arm_delta，这是所有 delta 累加的基准。

加了 `INIT_STATE = -7.0` 帧修掉。**单独修它没改变分数** —— 但原来那样是错的。

## 5. 和 zjw 推理侧的参数差异

他的 per-case `metrics.json` 记了完整推理契约，**读它，别猜**。

| 参数 | zjw | 我们（原） | 影响 |
|---|---|---|---|
| `max_target_step_rad` | **100.0** | 0.05 | 他在 100.0 下仍报 333 次裁剪 → 0.05 每步都在削 |

一个我更正过的判断：`model_action_from_joint_target` 对 exp04 是**恒等映射**
（`_ee_arm_converter is None`），所以不存在"空间错配"，差异只在「裁剪前 vs 裁剪后」。

## 7. 两个方法论教训

**CPU smoke 测试通过 ≠ 正确。** 我的 smoke 喂的观测几乎不变，相邻动作差异恰好接近 0，
完美掩盖了 tolerance=0 的 bug。**验 chunking 必须看 `calls_per_tick`**，
不能只看「动作有限、往返成功」。

**别停在第一个找到的 bug。** 修完 C 分数没动（仍 0/4），修完 D 也没动 —— 正是这两次
「修了但没变」把我指向 A 和 B。如果 C 修完就宣布收工，会得出一个仍然是错的数字。
