## 2. 划分：env 是资产，case 是轨迹

```
env  = 一个物体资产 = envs/<env_id>/ 一个目录        22 个
case = 一条轨迹     = cases.json 里一行             95 条(自 130)
```

这与 `bench_cube_val` / `bench_multi_val` **同构**：436 条 objaverse case 也是
一份 catalog + per-case pin，不是 436 个目录。所以「每 task 一 env」这个印象
在平台的任何一个包里都不成立。

## 3. 为什么 22 不是 130 —— 三条实测

130 是轨迹数。仿真要 spawn 的是物体资产。三条都测过，不是推的：

**支撑面高度已被归一化掉。** pointflow 那步把每个 task 的支撑面重基进 `goal_traj`：

| support | n | world z0 均值 | base 系 z0 均值 |
|---|---|---|---|
| floor | 10 | 0.0476 | 0.0464 |
| low_table | 32 | 0.4712 | 0.0247 |
| table | 88 | 0.9133 | 0.0053 |

world frame 差 0.87 m，base 系全落在离桌面 0.005–0.046 m。`world_z − base_z`
跨 −0.005→1.126（std 0.29）—— **不是减了同一个 robot_base**，per-task 面高
真的被吸收了。所以 support 和 z0 **不是 env 轴**，一个桌面高度服务全部 130 条。

**一个名字一个资产。** 22 个 mesh basename，每个在 130 个 task 里只有**一个**
sha256（0 个 basename 带多个哈希）。`points_obj` 在共享同一 env 的 task 之间
**逐位相同**（bowl 有 43 条）。表面点取决于资产，不取决于轨迹。

**带后缀的 uid 是场景实例。** 26 个 uid 收成 22 个资产：
`akita_black_bowl_{1,2,3}` / `butter_{1,2}` / `yellow_book_{1,2}` 各共享一份 mesh。
`new_salad_dressing` 与 `salad_dressing` 字节相同 → **21 个真实几何、22 个名字**
（记为 `geometry_aliases`）。

被否掉的三种划分：**130 个目录**（79 个会是同一 env 换个路径，而 `pointflow/`
已有的 130 份 mesh 重复就占了 116M 里的 106M）；**51 个 `(object, support, z0)`
组合**（三个轴里两个是假的，见上表）；**23 个 bddl 场景**（横切资产，一个场景装几个物体）。

## 4. env 目录的实际形态 —— 文档漏了 URDF

`STRUCTURE.md:16-19` 只列了三个文件。实际是五个，多出可 spawn 的资产：

```
envs/<env_id>/
├── mesh.npz          HOPE 扫描件 verts/faces/uv，verts 已是米
├── points_obj.npy    16 个规范表面点 float32 [16,3]
├── env.yaml          extent/bbox/sha256 + 哪些 LIBERO uid 与场景映射到此
├── <env_id>.obj      ← 文档未记
└── <env_id>.urdf     ← 文档未记，URDF 内按 <env_id>.obj 引用
```

22/22 都有 urdf + obj + mesh.npz + points_obj.npy + env.yaml。顶层另有
`object_urdf_index.json`。**`envs/` 实际 48M，不是文档写的 17M** —— 差的就是
后加的 obj/urdf。

**一个例外**：`alphabet_soup/` 有 12 个文件，多出 7 项
（`.usd` / `config.yaml` / `textured.obj` / `textured.mtl` / `texture_map.png` /
`textures/` / `usd_src/`）。那是 0813 单物体样例的遗留，**不是另一种契约**，
其余 21 个都是标准 5 文件。`verify_env_dirs.py` 22 项检查全过（含
`95 + 35 = 130`、cube suite 无损），所以这堆遗留不影响任何断言 —— 但值得知道
它为什么长得不一样，免得下次当成 env 目录的新标准去照抄。

## 8. 仍然成立的三个约束

**donor 的 cube 是 0.06 m，这些物体是 0.077–0.354 m。** `authored_episode.py` 靠
donor shard 合成 DerivedEpisode，而 donor 的规范点云是 0.06 m 立方体。这个替换
对手工 cube 轨迹是**精确**的，在这里**不精确**。`chefmate_8_frypan` 0.354 m =
cube 的 **5.9 倍**，Wuji 手没在任何接近的东西上训练过，它那 7 条该单独算，
不进 headline。**这是下一个决定，不是细节。**

**`viewers/` 里没有我们的手臂。** 抽一个 28M 的 viewer 数 token：`joint_pos` **0** 次，
`xarm` / `wuji` / `robot` / `link7` 都是个位数 —— 那是文字标签，不是几何（真有机器人
几何，每个 link 就是几千个顶点浮点数）。所以那 54 个页面渲的是**物体网格 + 目标轨迹**，
没有机器人。这与下面一条是同一个原因，不是遗漏。

要在图里放我们的手臂，现成的路子是 cube 线的
`bench_cube_val/tasks/build_task/build_reach_viewer_robot.py`：它从
`~/DexVerse-main/xarm7/.../xarm7_wuji_right.urdf` 取真实 URDF 网格，按
`T_world←link(frame0) @ T_link←mesh` 摆静态姿态，**但需要一份记录了 34 个 link 位姿的
pose npz**。LIBERO 侧没有这种文件（正是因为没有关节数据），所以手臂姿态只能借
donor（cube episode）的 —— **那是一个属于 cube 任务的姿态，不是这条 LIBERO 轨迹的姿态**。
画面能说明空间关系（手臂 / 物体 / 目标路径 / 可达包络），但不能标成「手臂在执行这个任务」。
`bench_libero/tasks/libero/pipeline/build_reach_viewer_realsoup.py` 是同一形状的成品
（真实扫描网格 + 真实 xArm7+Wuji URDF at home pose + DexVerse 桌面），可作模板。

**LIBERO 没有任何机器人关节数据。** 它是 Franka + 夹爪，我们是 xArm7 + Wuji 27 DoF。
`envs/episode.py` 要 `robot_joint_pos` / `_target`，所以 teacher replay 在这里
**结构上不可能**，不是没实现。也就是说：**cube 线那个「replay 闸门」在 LIBERO 上
拿不到**。而按 0827/0828 的教训，replay 闸门正是把「平台坏」和「策略差」分开的
唯一手段 —— LIBERO 上没有它，任何数字的解读都要更小心。

**指标含义变了。** `guide_tracking_*` 和 `demo_success` 本来对比 **teacher 录制**。
LIBERO 轨迹背后没有 teacher rollout，同样的公式测的是「与目标路径的一致度」——
**「跟没跟上」而不是「复现没复现」**。这些数**绝不能和 held-out shard 的结果平均**。

顺带重申两个跨文档反复出现的读数陷阱（0827 / 0829_new 都记过）：
`pos_err median` 的 PASS 在 policy eval 里无意义（物体不动时落在 float32 地板）；
`within3cm ≈ 0.69` 不是「跟得好」，是物体几乎没动过，永远和 `ever_lifted` 一起读。

## 9. 补上 cube 线缺的第三步：带机器人的渲染

cube 线是四步，LIBERO 前两步和第四步都已有，缺的是第三步「出带机器人的页」。
这次把它补上，并且**做成可复用模块**放在 `bench_libero/render/` 下，而不是又一个
一次性脚本。

| cube 步骤 | LIBERO |
|---|---|
| `author_reach_traj.py` 手工画轨迹 | 已有 —— 130 条真实 LIBERO 物体轨迹 |
| `goal_traj_to_pointflow.py` | 已有 —— `pointflow/` 130/130 |
| `build_reach_viewer_robot.py` 出带机器人的页 | **本次补上** |
| `build_authored_suite.py` | 已有 —— suite + 95 case index |

### 新增两个文件

**`render/robot_meshes.py`** —— 机器人几何的**唯一来源**。

抽取的动机是 Rule 0：这套逻辑当时已有**三份副本** ——
`bench_cube_val/tasks/build_task/build_reach_viewer_robot.py`、
`tasks/libero/pipeline/build_reach_viewer_realsoup.py`、
`render/render_stackcube.py`。三份都硬编码了同一个 js4 路径
`~/DexVerse-main/xarm7/...`，**本机不存在**。所以不是写第四份，是抽一份出来，
那三份以后往这里迁。

- `urdf_path()` 按优先级找本机 URDF（`pro5000_env/assets/urdf/...`，再退到
  `/mnt/venv_share/H800/Interprior/assets/urdf/...`），找不到就报出试过的每个路径
- **`meshes_from_joints(q)` —— 27 关节角走 FK**（`yourdfpy.update_cfg`）。
  这条是 LIBERO 必需的：`meshes_from_body_poses` 要的那份
  `body_names`/`body_pos`/`body_quat` npz 是 js4 遗留，**本机根本没有**，
  所以照 cube 线原样搬过来是跑不起来的
- `meshes_from_body_poses()` 原录制位姿路径**保留不动**，好让那三份副本平移
- `donor_joints(shard, ep, frame)` 从 donor shard 取 `robot_joint_pos`
- `derive_table_and_base(table_urdf)` 按 env 代码同样的算法从桌子 URDF 反推

关节序是坑：donor 的 27 维按 `ORDER`（7 臂 + 5 指 × 4），而 `yourdfpy` 的
`actuated_joints` 顺序不一定相同，`meshes_from_joints` 内部做重排 —— 这正是
不能让调用方自己内联 FK 的原因。

**`render/libero_task_viewer.py`** —— 单 case 出静态 HTML。
`--case N` 或 `--stem <名字>`，物体按 `goal_traj` 逐帧驱动，43 个 link 静态摆位，
圆桌，时间轴可拖。`render/__init__.py` 原本是空的，现在导出 `robot_meshes`。

### 常量对不上，按真值重推

两份副本的 `ROBOT_BASE` 不一致（`(0,0,0.53)` vs `(0,-0.08,0.53)`），`CUBE` 是
0.05 vs 0.06。**没有抄任何一个**，从冻结 profile 一路推：

```
table_round_large.urdf   <cylinder radius=0.7 length=0.3> at origin
                         → 中心 (0,0)、top offset 0.15
robot_base_on_table_center: true
scene_utils.py:2112      robot_initial_pos = (cx, cy, table_reset_z + top_offset)
simtoolreal_env_cfg.py:470   table_reset_z 默认 0.38
                         → ROBOT_BASE = (0, 0, 0.38+0.15) = (0, 0, 0.53)
profile object_size_m [0.06]³ + cube_0p06m.urdf   → CUBE = 0.06
```

结论：`build_reach_viewer_robot.py` 对，`render_stackcube.py` 的 `y=-0.08` 属于
**另一个 env**（js4 那张方桌，见「js4 vs txy 环境漂移」），`CUBE=0.05` 也不对。
推导连文件行号写进模块开头的 CONSTANT PROVENANCE 了，免得下次再各写一份。

### 几何校验（case 0，akita_black_bowl，K=197）

- **物体起始正好落在桌面 `+0.0000 m`** —— 独立验证了第 3 节那条「pointflow 已把
  支撑面高度吸收」，这次是从渲染侧反过来验的
- 目标路径 xy 半径 0.449–0.623（桌 r=0.70 内），最高 0.830
- 手臂 z 0.530→1.074、xy 到 0.508，与物体同坐标系
- 物体起点距底座 0.450 m，在 donor 实测可达 0.907 内

**坐标系是静默陷阱**：`goal_traj` 是**基座系**（pointflow 已重基），机器人网格出来是
**世界系**，物体必须加 `ROBOT_BASE` 才对齐。搞错不会报错，物体会浮空或沉进桌子。

复用性验过：frypan（case 50，那个 5.9× 的 oversize）K=184、wine_bottle（case 90）
K=309，同一条命令出页，43 link 不变。四道闸门重跑全绿
（`verify_env_dirs` / `verify_object_urdf` FAILURES 0、import 干净、cube 线未受影响）。

### 两个限制

**手臂姿态是借的**，来自 donor 的 **cube episode**（frame 0 home pose）。页面左上角有
橙色横幅写明 —— 只说明尺度和可达关系，**不是手臂在执行这条 LIBERO 轨迹**。
物体和路径是真 LIBERO 数据。这是第 8 节那条「没有关节数据」的直接后果。

**页面要联网**：three.js 走 unpkg importmap —— 这是本仓库**所有** viewer 的既有做法
（那 130 个也一样），几何本身烤进 HTML。要真离线得另做本地 vendoring。

### 建了什么

```
build_env/extract_libero_props.py    在 js4 跑（LIBERO 装那儿），--name X 或 --all
    ↓ tar 中转（js4 连不上 server2，Permission denied (publickey)）
tasks/libero/props/<category>/mesh.npz    verts [N,3] float32 米, faces [M,3]
tasks/libero/props/props_registry.json    source_xml + geom 统计 + articulated_baked
tasks/libero/props/PROPS_PIPELINE.md      190 行，坑都在里面
    ↓
render/libero_task_viewer.py --case N     自动从 envs/ 或 props/ 解析每个物体
```

加新类别是一个 `--name`，不改代码。**解析不到会明确报 `UNRESOLVED`** 并在页面标橙 ——
正是静默丢弃让「碗悬空」藏了这么久。

细节都在 `PROPS_PIPELINE.md`，这里只记三个最容易再踩的：

- **三种网格格式**，`trimesh` **读不了 MuJoCo `.msh`**，自己解析的（4×int32 头 + float32
  顶点/法线/uv + int32 面）。不做就丢 `cookies` 和 `white_cabinet`
- **视觉 geom 不全是网格** —— `flat_stove` 的炉面是 `type="box"`；且必须按 `group="1"`
  筛，否则柜子那 7 个碰撞盒会漏进渲染
- **scale 逐网格读**，跨度 0.0045（`wine_rack`）到 1.5（`desk_caddy`），不能假设

### 校验：0.000 m

补上柜子后实测：

```
碗终点     world [0.539, -0.314, 0.758]
柜子顶面   world z 0.758
差          -0.000 m          水平最近 0.080 m（在柜子footprint内）
```

**这个吻合不是拟合出来的** —— 柜子位姿来自 LIBERO 的 `all_poses`、网格来自 LIBERO 的
MJCF、碗轨迹来自 `pointflow/`，三个独立来源落在 0.000 m。这是目前对「整条链的坐标系
都是对的」最强的证据。

关键在坐标系的处理方式：`goal_traj` 是**基座系**，`all_poses` 是**世界系**，
偏移**从目标物体自己的首帧位姿反推**：

```python
shift = all_poses[target_index, 0, :3] - goal_traj[0, :3]
```

而不是再去推一个 `ROBOT_BASE` 常量。这样 props 和目标物体**按构造对齐**，不依赖我对
常量的独立推导 —— 这就是为什么能对到 0.000 而不只是「接近」。搞错不报错，物体浮空或下沉。

### 三个限制

**articulation 按决定烤成静态。** `flat_stove` / `white_cabinet` / `microwave` /
`wooden_cabinet` 在 LIBERO 里带关节（抽屉、门、旋钮），全烤成一个静态网格，
`props_registry.json` 标 `articulated_baked: true`。直说后果：case 0 的任务是
「**关上抽屉**，把碗放上面」—— 前半在静态资产上**无法评分**，而 **70/130** 场景含
baked 类别。

**白柜与木柜共用几何。** 七个部件 `.msh` 逐个 md5 相同，LIBERO 只靠贴图区分
（`white_wood.png` vs `dark_fine_wood.png`）。只烤几何，所以**渲染上分不出这两类**，
要区分只能查 `props_registry.json` 的 `source_xml`。

**decimation 目前失效。** `dexverse` 环境缺 `fast_simplification`，`basket`（66390 面）
和 `desk_caddy`（24970）原样通过，提取器会告警但保留完整网格。代价：`basket/mesh.npz`
3.2MB，用它的 22 个场景会出胖页面。

## 12. 教训

**「每 task 一 env」这种印象要靠测量推翻，不能靠回忆确认。** 130→22 的三条依据
（支撑面已归一化、一名一 sha256、后缀 uid 是场景实例）每条都是量出来的，
`build_env/README.md` 专门记了这些测量。如果当初照印象建了 130 个目录，
79 个会是同一个 env 换个路径，而且要到 spawn 的时候才发现。

**自称「生成」的文档比手写的更危险。** suite yaml 头一行写着
`GENERATED by build_env_dirs.py -- do not hand-edit`，同一段里又写着权威口气的
`NOT YET RUNNABLE`。两句都是假的：没有任何脚本写那个文件，而 `driver.py` 早已接上
`authored_npz`。手写文档过期会被人当过期看，**自称生成的文档过期会被当成契约** ——
我自己就照那行字判断过「改这条得改生成器」，直接错了一轮。
碰到「GENERATED by X」，先 grep 一下 X 到底写不写这个文件。

**一个正确的推导可以支撑一个错误的结论。** `STRUCTURE.md` 论证「22 个 env 不是 130」的
三条依据全部成立 —— 目标资产确实只有 22 种。错的是把「env」等同于「目标物体」：
**env 是一个场景，而场景有约 5 个物体。** 这一个概念混淆让 120/130 的场景都不完整，
而它能藏这么久是因为缺的全是静态物体 —— 不报错、目标照样动、只有终点几何会露馅。
推导没错不代表结论没错，要单独去问「这个结论回答的是不是我要问的问题」。

**「我看不见东西」是最有价值的 bug 报告。** 这轮两个真 bug 都是从「桌子是斜的」
「只看到一只碗」问出来的。第一个是 three.js 默认 Y-up 而场景是 Z-up；第二个是整个
benchmark 缺 11 类物体。两个我自己都没发现，因为我校验的是**数字**（顶点范围、
坐标系对齐），而数字全是对的 —— 缺的东西不会在它自己的校验里出现。

**同一个能力有三份副本时，第四份的成本是隐性的。** `robot_meshes.py` 抽取前，
机器人几何有三份实现，三份都指向同一个不存在的 js4 URDF 路径，且 `ROBOT_BASE`
和 `CUBE` 已经漂成两套值。真正的代价不是重复的行数，是**没人知道哪份的常量是对的** ——
必须回到冻结 profile 和 env 代码去重推。抽取时把推导过程连行号写进模块头，
比只写一个正确的数字有用得多。
