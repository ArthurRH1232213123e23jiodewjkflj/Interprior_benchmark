# 0908 — 评测改成「一 case 一进程」，渲染补齐到能看

本文记两件事：**评测怎么跑**变了，**一次 run 产出什么**也变了。起因是 0907 留下的
两个尾巴：动态场景物体建好了却对输出没有任何影响，以及多 env 在 reset 时崩。

结论先说：

- **多 env 放弃了。** 不是修不好，是它和「带家具的场景」互斥 —— props 是**每 case
  烤一张复合桌**，而 env 只吃一张桌子。多 case 一进程只能 `--no-props` 跑，那是一个
  没有柜子和篮子的场景，而**目标终点就落在这些家具上**。
- **分片改成一 case 一进程，GPU 当池子。** 并行度不变，靠的是卡数而不是进程内 env 数。
- **渲染两处硬伤修完**：mesh 从来没被内联进页面，场景物体从来没被采集。后者意味着
  0907 那个 commit 的输出和它之前的那次**逐字节相同**。
- **页面 79.75 → 15.82 MB**，两步都无损。
- **0907 的 dynamic spawn 是建对的**，现在有证据；真正的缺陷是另一个：**8 个物体
  出生在圆桌外面**。

---

## 1. 0907 留下的两个尾巴

0906 日记第 11 节第 3 条写着「props 只进了渲染没进 eval，在这之前任何 LIBERO 的
rollout 数字都是在错的场景里跑出来的」。0907 做的正是这条：先把 props 焊进桌子，
再把每个 case 自己的非目标物体 spawn 成动态刚体。

物理侧确实做成了。但有两件事当时没发现：

**输出没有任何变化。** `0907_case11_dyn2` 的 rollout 页面和 17:06 那次（动态物体
commit 之前）**md5 完全相同、字节数完全相同**。一个 feature 落地了，输出一个 bit
都没动。

**多 env 在第一次 reset 就崩。** `write_reset_poses` → `set_transforms` 报 CUDA
device-side assert。当天最后写了个 `probe_scene.py` 想查物体到底落在哪，它挂了 15
小时没出结果。

## 2. 为什么放弃多 env

### 不是因为那个崩溃

排查顺序和结论：

| 怀疑 | 结论 |
|---|---|
| `replicate_physics` 没关（per-env 不同 USD 的经典坑） | **排除**。上游 `simtoolreal_env_cfg.py:687` 已设 `replicate_physics=False` + `clone_in_fabric=False`，注释里写明了原因 |
| 位姿数据脏（NaN / 零四元数 / 越界） | **排除**。离线把 multi4 四个 case 要写的 18 个位姿全打出来，无 NaN、四元数全归一、位置全在桌面范围 |
| 空槽停在 `PARK_Z = -5.0` | **未证实**。case11 无空槽跑通、multi4 有空槽崩，相关性干净，但没做对照 |

对照实验设计好了（case 5+6 物体数相同 vs case 5+2 不同，目标物体都是
`akita_black_bowl`，唯一变量是空槽），**但没跑完就不需要了** —— 它撞上了下面这个
更根本的东西。

### 而是因为 props 和多 case 互斥

第一个对照跑起来直接被 driver 挡下：props 是**每 case 烤一张复合桌**，env 里桌子却是
全场景单值。这和 0829 记的 `object_urdf` 全局单值是**同一个形状**，只是这次落在
table 上。

于是多 env 只剩一条路：`--no-props`。0907 的 multi4 正是这么跑的 —— 也就是说那次
多 env 尝试**从一开始就是没有家具的场景**。而 72 个 case 里大量任务的终点是「放进
篮子」「放到柜顶」「放上盘子」。**就算那个 CUDA 崩溃修好了，跑出来的也不是我们要
评的任务。**

### 成本核算：放弃它不亏

| 方案 | 家具 | 全量 72 条耗时 |
|---|---|---|
| 一 case 一进程 + 8 卡分片 | **有** | 约 11–30 分钟 |
| 多 env | 无（必须 `--no-props`） | 更快，省的是 Isaac 启动开销 |

实测单 case 冷启动约 3.3 分钟（Isaac 启动占 166 秒）、热启动且不出页面约 70 秒。
按后者，72 条 8 卡约 11 分钟。**对一个评测平台，这个数完全可以接受**，没有理由
为了省启动开销去换一个错误的场景。zjw 本来也是一 case 一进程。

## 3. 新的评测流水线

`api.py` 原来把 suite 按 GPU 数切成 N 片，每片多个 case 在一个进程里当 N 个 env。
现在：

**分片按固定大小切，`cases_per_process` 默认 1。** 这个默认值不是性能选择，是上面那条
硬约束；注释和 `--cases-per-process` 的 help 里都直说了为什么，免得后人当成可调参数
随手调大。

**轮转从「case→分片」移到「分片→GPU」。** 每张卡一个线程，顺序跑自己那批。并发度是
**卡数**而不是分片数 —— 一个分片一个线程的话，72 个 case 会一次拉起 72 个 Isaac 进程。

**分片目录必须改名。** 原来是 `gpu{n}`，只在「一张卡一个分片」时唯一。一张卡跑多个
分片后，后一个会覆盖前一个的 `summary.json`，而 `_merge` glob 的是
`gpu*/summary.json` —— 结果会**把每张卡的最后一个 case 当成整个 suite 的成绩报出来**，
而且所有闸门全绿。这是本 package 反复出现的失效形状（436-case object pin、xhand
立方体、按 case_index 查 props）。现在是 `gpu{n}_s{k:03d}`，仍以 `gpu` 开头所以那个
glob 不用改。

验证：`libero_ctl_equal`（2 case）在 GPU 6,7 上跑，2 个分片各 1 个 case，**两片都带
家具**、各 2 个动态场景物体，目录分开，`report.json` 正确合并 2 个 case。同一个 suite
在改之前是直接 `SystemExit` 的。

## 4. 渲染：两处硬伤

页面里看不到物体，是**两个**独立缺陷叠在一起。

### mesh 从来没有被内联

`flow_viewer` 对 object / table 用的是 `_rewrite_embedded_urdf_mesh_urls`。那个函数把
相对 mesh 文件名改写成 github raw URL，**但只对落在 Interprior REPO_ROOT 内的 mesh
生效** —— `_raw_url_for_repo_path` 对 root 外的路径返回 None，循环随即跳过，**原样
保留相对文件名**。

LIBERO 的 mesh 全在 root 外（`tasks/libero/envs/…` 和每次 run 的
`scene_table/<case>/*.obj`），所以 10 个引用全部以裸文件名 `filename="xxx.obj"` 留在
HTML 里，单文件页面无法解析。页面于是只画出机器人（它的 72 个 mesh 走的是另一个
函数 `_embed_urdf_mesh_data`，是 data URI）和桌面那个 cylinder 图元。

**静默**：mesh 取不到既不画也不报。

改成 object / table / hole 都走机器人一直在用的那条内联路径（支持 `.obj`）。

### 场景物体从来没有被采集

上游 `capture_pose_viewer_frame` 读的是**硬编码的五个**：robot / object / goal_viz /
table / hole。它不可能知道我们 append 上去的刚体。所以 0907 的动态物体**在 sim 里，
但不在任何页面里** —— 这就是那两个文件 md5 相同的原因。

补法（三段，最后一段几乎免费）：

| 段 | 做了什么 |
|---|---|
| 采集 | 新增 `scene_spawn.capture_poses`，按 env-local 读位姿，和上游 capture 同一坐标约定；空槽跳过 |
| 携带 | driver 每个捕获帧写入 `frame["scene_object_poses"]`；`rollout_viewer` 栈成 `[T,7]` |
| 渲染 | `flow_viewer` append 进 `robots` / `object_poses` —— 这层本来就是通用的（flow marker 早就在利用它） |

两道断言，因为「看起来对但其实错」是这个 package 的惯犯：物体集合中途变化就报错
（否则会拿 A 的轨迹去画 B），名字撞上 robot/table/object/hole 就报错。

## 5. 位姿第一次被看见

位姿进了页面，才第一次能逐个核对。**0907 建的是对的**：

| 物体 | 表现 | 判定 |
|---|---|---|
| `plate_1` | 0.5304 → 0.5290，1.4 mm | 落在桌面上，1.4 mm 是解穿模 |
| `akita_black_bowl_2` | 0.7395，全程不动 | 悬空 21 cm 却不掉，一度极可疑 —— 直到量出 `wooden_cabinet` 网格顶面在 **0.7397**，差 **0.2 mm**。它站在柜顶上 |

之前发现不了，是因为 **`verify_spawn` 只比对名字，不比对位置**。一个只验身份不验状态
的闸门，能让错误的物理躺很久。

### 三个「掉下来」的物体是对的

showcase 那条（番茄酱放进篮子）里 ketchup / milk / orange_juice 从半空掉到桌面，
第一反应是「托着它们的家具没建」。**错了。** 把 LIBERO 自己录的轨迹调出来比：

| 物体 | LIBERO 录的（base z） | 我们的 sim |
|---|---|---|
| ketchup_1 | +0.1976 → +0.0755 | +0.1956 → +0.0737 |
| milk_1 | +0.1561 → +0.0729 | +0.1540 → +0.0712 |
| orange_juice_1 | +0.1561 → +0.0729 | +0.1540 → +0.0718 |

**LIBERO 自己就让它们从半空落到桌面**，我们复现到 2 毫米以内。这正是 `scene_spawn`
文档里那个设计的意图（用第一帧的悬空位姿让动态物体自己落下去，而不是去猜「该用第一帧
还是稳定帧」），现在它被验证了。

顺带排掉「没加载全」的怀疑：72 条 case 的 `unresolved` **全空**，没有一个类别被静默
丢掉；家具也不是不支持 —— shelf / wine_rack 在别的 case 里出现了 16 次
（wooden_cabinet 20、flat_stove 19、desk_caddy 14、basket 13…）。`living_room_scene2`
就是只有一个篮子。

## 6. 真正的缺陷：8 个物体出生在桌外

`cream_cheese_1` 在 LIBERO 里全程稳在 +0.0120，在我们这儿**掉了 0.533 米到地上**。

圆桌半径 **0.70 m**，它的出生点距桌心 **0.7039 m** —— 出生就在桌沿外 4 毫米。
LIBERO 的桌子比我们的圆桌宽，那 4 毫米在原场景里还在桌面上。

全量扫描：**8 个物体、8 条 case**（r 0.704–0.740）的场景物体出生在圆桌外，其余 178 个
都在桌上。

| suite_pos | env | 物体 | r |
|---|---|---|---|
| 18 | akita_black_bowl | akita_black_bowl_1 | 0.724 |
| 32 / 33 | black_book | red_coffee_mug_1 | 0.722 / 0.740 |
| 43 | cream_cheese | tomato_sauce_1 | 0.710 |
| 53 | porcelain_mug | plate_2 | 0.730 |
| 58 / 59 | tomato_sauce | cream_cheese_1 | 0.704 / 0.714 |
| 68 | wine_bottle | plate_1 | 0.705 |

注意 `reachability_report` 查的是**目标物体轨迹**的 xy 包络，**从来没查过其他物体的
出生点**。三条路：改大桌子半径（会动冻结的 physics profile，等于改契约）、像
reachability 那样标出来单独处理、或把出生点往内夹（改了就不是 LIBERO 的场景）。
**倾向第二条，未定。**

## 7. 页面体积：79.75 → 15.82 MB

先量再改。测出来页面 **100% 是 mesh 的 base64**（79.62 / 79.75 MB），轨迹和 JS 加
起来只有 0.13 MB。

| 步骤 | 大小 | 原理 |
|---|---|---|
| 原始 | 79.75 MB | |
| 去 collision | 50.33 MB | 页面里从没出现过 `parseCollision`，urdf-loader 默认 false —— 那 **29.4 MB 从头到尾没被解析过**。URDF 里 `<visual>` 和 `<collision>` 指着同一个文件，base64 被塞了两遍 |
| `.obj` → glb | **15.82 MB** | ASCII 的 `.obj` 是所有格式里最费的。这些 mesh 由 `mesh.npz` 生成，**只有 `v` 和 `f`**，没有 uv / 法线 / mtl，所以转换在严格意义上无损。实测篮子 66,390 面：7.39 MB → 1.20 MB |

**不影响物理。** 改的只是「塞进 HTML 的那份拷贝」，磁盘上的 URDF 一个字没动；
`scene_spawn.spawn()` → `_convert_urdf_to_usd` → `_bake_usd` 读的还是原文件。同一个
文件，两个互不相干的读者。

`<collision>` 是**整个删掉**而不是留个空文件名 —— 留裸文件名正是本文第 4 节那个坑，
只要有人把 `parseCollision` 打开就会重新踩。想看碰撞体用 `--viewer-collision`。

转换结果按**源文件内容 hash** 缓存在 `~/.cache/bench_libero/glb/`，mesh 变了自动失效。

## 8. 全平台打开机器人自碰撞

起因是两个怀疑：**手的 mesh 有问题**，以及**碰撞解算步数不够**。查下来第一个说对了
症状、说错了位置，第二个暂时没有问题。

### 不是 mesh，也不是导入

URDF 源头干净：5 个 `right_finger{1..5}_tip_link` 和 `right_palm_link`，
visual / collision / inertial 一个不缺。

导入时 Isaac 确实把指尖并进 `link4`、手掌并进 `link7`，还打了 DEPRECATION 警告
（「has body properties (mass, inertia, or collisions) and is being merged」）——
看起来很像元凶。但把 URDF importer 自己写下的 `config.yaml` 和
`~/Interprior_exp` 里开着自碰撞的那些跑法逐项对比，**合并行为两边完全一样**：

`merge_fixed_joints: true`、`collider_type: convex_hull`、`fix_base: true`、
`link_density: 0.0`、`joint_drive` 全同。**唯一的差异是 `self_collision`。**

### 关掉自碰撞意味着什么

PhysX **根本不检测手指与手指、手指与手掌之间的接触**。手可以穿过自己闭合，可视化里
手指互相 clipping（0827 那条「suspect it on clipping/finger-joint singularities」记的
就是这个），而且**一个物理上不可能存在的手型照样能被判成「抓住」**。

### 为什么它能一直躺着

`assets.robot_self_collision_enabled` **不在** bench_cube_val 和 bench_libero 的
`REQUIRED_FIELDS`，也不在 `ADVISORY_FIELDS`。闸门不查，于是三条线全都静默吃 env 默认值
（`false`），没有任何东西会提醒。这和 `REQUIRED_FIELDS` 里桌子几何那几行的注释描述的是
同一个形状：**「缺失的键会回落到 env 默认值，这正是它没被发现的原因，所以两个都必须查」**。

`bench_multi_val` 是唯一列了这个字段的，也正因如此，唯一一份历史上的 selfcoll profile
在那边。

### 做法：新建 profile，不改冻结那份

`summary.json` 同时记 profile 的**名字**和 **sha256**。原地编辑冻结文件会让名字不变而
hash 变，**所有历史数字会静默失去可比性**。所以每条线新建一份，和源文件逐字节相同、
只差那一行，头部记源文件名 + 源 sha256 + 理由：

| benchmark | 新 profile | 重指的 suite |
|---|---|---|
| bench_cube_val | `tro_mp_dataprod_venvshare_20260808_selfcoll.yaml` | 5 |
| bench_multi_val | `tro_mp_objaverse_zjw_eval_pairing_20260826_selfcoll.yaml` | 1 |
| bench_libero | `tro_mp_dataprod_venvshare_20260808_selfcoll.yaml` | 9 |

同时把 `assets.robot_self_collision_enabled` 加进三条线的 `REQUIRED_FIELDS`，闸门
**23 项 → 24 项**，以后不能再静默漂移。

验证（`libero_one_case11`）：闸门 `ok=True checked=24 mismatch=0`，URDF converter 自己写的
`config.yaml` 变成 `self_collision: true`。

### 代价，已提出并决定照做

cube 线和 multi 线的 teacher 数据是在 `false` 下产出的，**评测物理从此和数据生产物理
不一致**，0908 前后的数字不可直接比。这一点提出过，决定是全平台打开。好在 profile 名和
hash 都变了，**断裂是可见的而不是静默的**。

LIBERO 没有这个问题：它的目标轨迹来自 LIBERO 自己的录像，本来就没有在这个 profile 下跑出来
的 teacher rollout 要对齐。

### 碰撞解算迭代：暂时没问题

profile 是 scene position 8/64、velocity 0/64、robot articulation 16/8，和之前那次修复
（max_pos 64 / robot 16）对得上，而且这 6 个字段本来就在 `REQUIRED_FIELDS` 的最前面，
注释写着「**这是整张表里最重要的一行**」。

我们 spawn 的场景物体和上游**目标物体**用的是逐字相同的 bake props（都不设 solver 迭代，
都吃 scene 下限），所以场景物体不比目标物体弱。

**一条待查**：PhysX 运行时警告 `articulation ... with more than 4 velocity iterations
being added to a TGS scene`（机器人要 8）。TGS 对 >4 的速度迭代处理方式变过，需要确认这个
设置是真生效还是被降级了。

## 9. 未验证 / 下一步

1. **页面能不能显示，仍然没有被证明。** 无头 Firefox 在这台机器上报
   `RenderCompositorSWGL failed mapping default framebuffer` —— 它没有可用的 GL，
   渲不出来是环境问题，**不能当作页面的证据**。需要在有 GL 的地方打开确认。
2. **8 个出生在桌外的物体怎么处理，未定**（第 6 节三条路）。
3. **PARK_Z / 空槽那个 CUDA 崩溃没修**，也不打算修 —— 多 env 已放弃。如果将来有
   `--no-props` 的批量需求（比如纯 open-loop 探针），它会重新变成拦路石。
4. **decimation 还是失效的**（0906 记过）。`fast_simplification` 没装，而
   `~/pro5000_env` 那个 venv symlink 到共享树，往里装包会影响这台机器上别人的任务。
   要做得装到独立目录再挂 sys.path。装上后页面可以从 15.8 MB 再降到 5 MB 以内。
5. **全量 72 条还没跑过。** 新分片只在 2 个 case 上验过。
6. **TGS 场景下机器人 8 次速度迭代是否真生效**（第 8 节末）。
7. **自碰撞打开后 grasp 数字怎么变，还没量。** 应该拿同一条 case 做 A/B：看 grasp
   成功率变化，以及可视化里手指 clipping 是否消失。
8. **仍然是 `teacher_replay`。** LIBERO 没有机器人关节数据，手臂全程不动、物体不会被
   拿起来。场景现在是完整的，**动作不是**。要看到动作完整的任务必须接策略跑
   `run --policy`。

## 10. 教训

**「输出逐字节相同」是最强的回归证据。** 0907 那个 feature 落地了、闸门全绿、日志里
写着「2 dynamic body(ies) verified」，而输出文件 md5 和 feature 之前的那次一模一样。
**新增一个能力之后，先去看输出有没有变**，比读日志里的成功行有用得多。

**只验身份不验状态的闸门，能让错误躺很久。** `verify_spawn` 逐名比对物体，防住了
「拿错 case 的场景」这一类错误 —— 但它不看位置，所以物体沉进桌子、悬在半空、穿模，
一个都发现不了。**闸门要问的是「它现在是什么状态」，不只是「它是谁」。**

**下结论前先去问真值怎么说。** 看到三个物体从半空掉下来，我直接判成「缺家具」，还
写进了汇报。真值就在手边 —— LIBERO 自己录的轨迹显示它们本来就是掉的，我们复现到
2 毫米。**一个现象有合理的解释，不代表那个解释是对的。**

**别拿自己没验过的工具当证据。** 我用无头 Firefox 去截图证明页面能不能显示，跑了几
分钟没出图。差一点就写成「页面渲染失败」——实际上是那台机器的无头模式根本没有 GL。
**工具本身要先被验证，否则它的沉默什么都不说明。**

**闸门里没列的字段，等于没有保护。** `robot_self_collision_enabled` 三条线全都躺在
env 默认值上，因为两条线的 `REQUIRED_FIELDS` 里没有它。profile 里写没写这一行都不重要 ——
**不被检查的配置项迟早会漂**，而漂的时候不会有任何声音。发现一个这样的字段，除了改值，
还要把它加进闸门。

**症状指对了地方，不代表病因也在那里。** 「手的 mesh 有问题」这个判断是对的 —— 手指确实
在穿模。但 mesh 是好的、URDF 是好的、导入设置也是好的，问题在一个和 mesh 毫无关系的开关
上。**逐项对比一个已知正确的参照**（这里是 `Interprior_exp` 里开着自碰撞的那份
`config.yaml`）比顺着症状往下挖快得多。

**先量再改。** 压体积之前先把 79.75 MB 拆成 visual / collision / 每个 body，才发现
最大的一块（29.4 MB）是浏览器从来不读的东西。如果按直觉先去做 decimation，会花最大
的力气拿最小的收益，还会损失几何精度 —— 而真正该做的两步都是无损的。
