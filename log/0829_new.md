# 结构与用法（2026-08-28 重组后）

`interprior_bench` 已拆成**每个 benchmark 一个包**。包名就是 benchmark 的选择，
不再靠参数传。

## 用法

commands: 
task
verify
replay
run

```bash
python -m bench_cube_val  replay --cases 8 --gpus 2,3,4,5    # 单方块，物理闸门
python -m bench_multi_val replay --cases 8 --gpus 2,3,4,5    # 多物体（骨架，见 §4）
```

命令面：`tasks`（列 suite）、`verify`（物理闸门）、`replay`（teacher 回放）、`run`（评策略）。

## 2. 一条规则：路径从包自身推导，不写包名

```python
# api.py
WORKER      = PACKAGE_DIR / "driver.py"
SUITES_DIR  = PACKAGE_DIR / "suites"
# driver.py
profile_path = Path(V.__file__).resolve().parent / "profiles" / suite.physics_profile
```

两个包是副本，任务语义（四类阈值、v10 指标、状态注入）会分头演进。路径里写死包名的话，
`bench_multi_val` 会**静默用 cube 的 driver 或 cube 的 profile** —— 物理闸门照样通过，
但比对的是错的基准。加新包时这是唯一必须遵守的约束。

## 3. suite 的三个偏移是独立的

```yaml
start_frame: 0            # 仿真从哪帧开始
plan_source_start: 121    # plan 从哪个源帧切  ← 与上面无关
max_frames: 647           # horizon → 切片 [121, 768)
```

第三个偏移（评分参考）在 driver 里跟着 `plan_source_start` 走。三者曾经只对齐了两个，
导致 `demo_success` 假报 0/200（真实 112/200）。见 `0828_error.md`。

647 是 exp04 ckpt 硬锁的宽度（`object_flow_plan_min/max_frames` 都是 647），
递更多会被静默截断。

## 5. 两个读数陷阱

- **`pos_err median` 的 PASS 在 policy eval 里无意义** —— 物体不动时落在 float32 地板，
  必然通过。只对 replay 有效。
- **`within3cm ≈ 0.69` 不是「跟得好」** —— 意思是物体几乎没动过。永远和 `ever_lifted` 一起读。
